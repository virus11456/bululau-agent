# 操作手冊

策略規則在 [strategy.md](strategy.md)。這份只講機器人怎麼跑、什麼時候該出聲、出錯時做什麼。

所有指令都在專案根目錄執行。下面用 `python3`，排程時請換成這台機器的絕對路徑。資料目錄用環境變數 `QUANTBOY_DATA_DIR`；不設的話就是專案下的 `data/`。

```bash
export QUANTBOY_DATA_DIR="/絕對路徑/bululau-agent/data"
```

金鑰從環境變數或 `.env` 讀，見 [README.md](../README.md)。終端機輸出與 `live_log.jsonl` 裡不該出現金鑰；若例外訊息裡帶了金鑰，先撤銷該金鑰再查原因。

## 實盤指令

| 指令 | 會不會送出委託 | 用途 |
|---|---|---|
| `python3 src/live_trader.py status` | 不會下單。會讀帳戶；台北時間跨日會重寫 `state.json` | 看淨值、持倉、掛單時間與單號 |
| `python3 src/live_trader.py manage` | 不會。仍會讀帳戶，7% 時會把「停開新倉」寫進狀態 | 預覽風控與保護單缺什麼 |
| `python3 src/live_trader.py manage --live` | 會。補保護單、必要時平倉 | 每一輪的第一步 |
| `python3 src/live_trader.py open ...` | 不會送出委託。會讀帳戶並呼叫 `/order/test` | 下單前看計畫 |
| `python3 src/live_trader.py open ... --live` | 會送出進場單，並掛停損、止盈 | 確認計畫之後 |
| `python3 src/live_trader.py watch --live` | 僅在待成交限價單需要補保護單時，才會下單 | 建議每分鐘跑 |
| `python3 src/live_trader.py flatten --live` | 會市價平掉所有倉，並取消所有掛單 | 只有使用者明確要求全部結束時才用 |
| `python3 src/prefilter.py --quiet` | 不下單、不需金鑰 | 機械篩選 |
| `python3 src/sentiment.py 幣種` | 不下單、不需金鑰 | 情緒濾網 |

同一時間只能有一個 `live_trader.py`。另一個還在跑時，後來的會直接結束並寫「另一個 live_trader 正在執行」。等它結束再跑，不要改下 `flatten`。

`status` 的掛單行帶有台北時間的「掛於」與 `id`。algo 條件單若交易所沒給建立時間，程式會改印其他時間欄，只拿來輔助，下單時間仍以日誌為準。

## 每 15 分鐘的一輪

1. 跑 `manage --live`。
   - 出現當日虧損 ≥ 30%、或已全平：停手。回報使用者。不要再開倉，不要刪旗標。
   - 出現 ≥ 7%、今日停開新倉：這一輪可以繼續看持倉與掛單，不可以 `open`。
   - 某個倉「缺停損」：程式會補掛；補掛失敗會市價平掉該倉。把日誌裡的錯誤一起回報。
2. 跑 `status`。一般掛單若是限價進場（`LIMIT`），而且「掛於」距現在超過 2 小時、狀態仍未完全成交：回報幣種、單號、掛上時間、價格。由使用者撤單。不要用 `flatten` 撤單，那會平掉所有倉。程式沒有「只取消這一張」的子命令。
3. 跑 `prefilter.py`。結束碼 2：這輪不做進場判斷，下一輪再試，除非同時有持倉風險要回報。結束碼 0：沒有機械候選，仍要看既有持倉該不該處理。結束碼 10：對每個候選逐條對 [strategy.md](strategy.md)。篩選用英文寫的失敗原因要讀，不能因為它是候選就進場。
4. 對準備進場的幣再跑 `sentiment.py`。`block` 或 `unknown` 不做。`caution` 只在回報裡註明，份數維持原計畫。忽略篩選結果裡的 `confidence_hint`（亞洲盤低信心是舊字串）。
5. 檢查紅線：BTC 關鍵價、事件窗口、5 倉、單幣是否已有倉、停損後三根 K 有沒有走完、是不是黑名單或妖幣條件不符。
6. 先不加 `--live` 跑 `open`。核對：
   - 方向是 `BUY`
   - 多單要停損 < 進場 < 止盈
   - `est_loss` ≤ `risk_cap`
   - 停損距離符合該型態的下限
   - `--portion` 是 `1`、`0.5` 或 `0.25`
   - `--setup` 用 `布鹿流`、`大師兄`、`小師弟`、`瘸師弟` 之一
   - 布鹿流的 `--target` 用進場價加 2R，當成減倉前的保護單
   - 瘸師弟的 `--target` 用 1.5R
   - 小師弟的 `--target` 落在 1.5R 到 2R
7. 核對無誤才把同一組參數加上 `--live`。下完立刻再跑 `manage --live`，確認該幣停損、止盈都在。限價單若止盈會被交易所以「立刻觸發」（錯誤碼 −2021）拒絕，程式會先掛停損、暫時不掛止盈，並在狀態裡留下 `pending`。`watch` 或下一輪 `manage` 應在成交後補上。若停損預掛失敗，程式會撤掉這張進場單；若已經成交則市價平倉。把這個錯誤回報使用者。
8. 有下列任一項才回報：開倉、成交、撤單、減倉、移停損、平倉、出錯、風控。沒有就不要發訊息。

## 回報格式

```text
【機器 代號】開倉
幣種／型態／BUY
進場、停損、止盈、數量、槓桿、份數
預估虧損、約等於幾 R、停損距離百分之幾
出處：布神原話／使用者決定／我們加的（這筆用到的那幾條）
情緒：ok 或 caution 的原因（caution 沒有降份）
```

風控回報要寫當日虧損百分比、程式做了什麼（停開新倉或全平）、旗標路徑。出錯回報要寫指令、幣安錯誤碼、倉位現在還在不在、停損還在不在。不要附上 `.env`、金鑰或簽章。

帳戶淨值可以寫在 `status` 的回報裡，那是使用者要看的數字。不要把淨值抄進 git。

## 減倉與移動停損

到 +1.5R 平一半、停損移到成本、布鹿流改掛波段低點，這些 **沒有子命令**。程式的 `manage` 只負責「有沒有停損、有沒有止盈」。

若持倉還在、狀態檔 `meta` 裡仍留著原來的 `target`，下一輪 `manage --live` 發現沒有止盈，會把原來的止盈補回去。所以不能先在交易所撤掉 2R 止盈、卻沒有同步處理狀態，否則保護單會被掛回。

這一版的做法：代理算出建議的減倉數量、新停損價、是否撤掉原止盈，然後停下來回報使用者，等使用者在交易所處理，或等以後有專用指令。不要為了完成出場去直接呼叫幣安 API，也不要手改 `state.json`。手改之後，跨日重置或下一輪 `manage` 可能和交易所不一致。

移停損的原則仍然是：先掛好新停損，確認委託存在，再撤舊的。由使用者執行時也照這個順序。

## 撤單

- 限價進場超過 2 小時未成交：回報單號，等使用者撤。連同該幣預掛的停損、止盈一起撤。出處：我們加的。
- 限價單被取消、過期，而且該幣已經沒有持倉：`manage` 會撤掉孤兒保護單。
- `flatten --live` 只在使用者明確說「全部平掉」時使用。

## 停損之後等三根

程式不記錄冷卻。平倉（含打到停損、保本、移動停損）之後，在資料目錄自行留下 `cooldowns.json`，這個檔不進 git，程式也不讀它：

```json
{
  "ETHUSDT": {
    "tf": "15m",
    "stopped_at": "2026-11-03T21:15:00+08:00",
    "resume_after_bars": 3,
    "reason": "stop"
  }
}
```

同一個幣在進場週期又收完 3 根 K 之前，不要開新倉。收完之後重新看型態，而不是時間到了就進。開倉成交後把該幣從這個檔移除。

## 重大事件檔

複製範例後自行維護：

```bash
mkdir -p data
cp config/events.example.json data/events.json
```

```json
[
  {"time_tpe": "2026-11-06T21:30", "title": "US NFP"}
]
```

`time_tpe` 不帶時區時，程式當成台北時間。事件前後各 30 分鐘，`open` 會拒絕。已有持倉不因此自動平倉。檔案缺失時程式不擋，看盤時要自己擋，並回報「事件檔不存在」這一次，補上檔案即可，不必每輪重複。

## 當日 reset 與停機旗標

時區是台北。狀態在 `data/state.json`。

- 日期變更的第一次 `status`、`open` 或 `manage`，會把狀態整份重寫：新的日初淨值、每份保證金、`halted_new=false`、`killed=false`。原來的 `pending` 與 `meta`（停損價、止盈價、型態名稱）會消失。
- 跨日之後，交易所上如果還有停損單，`manage` 看得到，就不會亂平。若跨日後停損單也不見了、狀態裡又沒有價格，`manage --live` 會把該倉市價平掉。跨日前先看一眼保護單還在不在。
- 當日虧損 ≥ 7%：寫入 `halted_new`。到了下一個台北日，這個旗標會隨 reset 清掉，可以再評估新倉。
- 當日虧損 ≥ 30%：市價全平、取消掛單、`killed=true`，並寫下 `data/HALT_REPORT_USER.flag`。跨日只會清掉狀態裡的 `killed`，**不會刪除旗標檔**。只要旗標還在，`open` 就會拒絕。使用者用文字明確同意恢復之前，不要刪檔、不要再加 `--live` 開倉。

## 出錯時

| 情況 | 程式行為 | 你要做的 |
|---|---|---|
| 金鑰讀不到 | 結束，訊息不含金鑰內容 | 檢查 `.env` 或環境變數，不要把金鑰貼出來 |
| 帳戶是雙向持倉 | `--live` 的 `open` 直接拒絕 | 在幣安改成單向之後再跑。有倉時先問使用者 |
| HTTP 429／418 或幣安 −1003 | 退避後重試，寫入 `live_log.jsonl` 的 `backoff` | 這一輪不要連續手動重跑很多次 |
| 5xx 或網路錯誤 | 有限次重試，仍失敗則結束碼非 0 | 回報。不要在失敗當下改用 `flatten`，除非使用者要求 |
| 市價進場後停損掛不上 | 立刻市價平掉該倉 | 回報錯誤碼與是否已平 |
| 限價進場後停損預掛失敗 | 撤進場單；若已有倉則平倉 | 回報 |
| 止盈掛不上，但停損已在 | 記錄錯誤，倉位留著 | 回報。下一輪 `manage` 會再試。−2021 則等成交後再補 |
| 有倉、沒有停損、狀態裡也沒有停損價 | 市價平倉 | 回報 |
| 篩選或情緒讀取失敗 | 篩選結束碼 2；情緒標 `unknown` | 不開新倉 |
| 檔案鎖衝突 | 後者直接退出 | 稍後重試該指令 |

日誌在 `data/live_log.jsonl`，一行一個 JSON。常見 `kind`：`open_plan`、`entry_order`、`protect_placed`、`market_close`、`daily_stop`、`kill`、`error`、`watch_trigger`、`limit_done`、`limit_dead`、`cancel_orphan`、`day_reset`。查問題時對時間與幣種即可。這個檔含有委託細節，不要提交。

## 紙上倉位檢查

`python3 src/position_manager.py` 只讀 `data/positions.json`，用已收盤的 15m K 棒模擬停損、止盈與時間停損，並把事件附加到 `data/decisions.jsonl`。檔案不存在時會直接結束並說明。

它的參數是舊的紙上規則（例如瘸師弟在 0.5R 移到成本、固定根數就出場）。不要對真實持倉跑它，也不要把它的出場當成實盤動作。`--dry` 只計算、不寫檔。

`positions.json` 若要做紙上演練，`open` 陣列裡每筆至少要有：`symbol`、`pattern`（`布鹿流`／`小師弟`／`瘸師弟`／`funding_rate`）、`entry`、`stop`、`opened`（台北時間的 ISO 字串）。可選 `target`、`status`（`pending` 或 `open`）、`id`。

## 和排程一起跑

- 每分鐘：`watch --live`。沒有 `pending` 限價單時行程幾乎立刻結束，也不會呼叫幣安。
- 每 15 分鐘：由 AI 代理跑完整輪，提示詞用 [agent_prompt.md](agent_prompt.md)。
- 不要另外再排一個會下單的 `manage --live` 跟代理重疊。代理這一輪自己會跑 `manage`。每分鐘的 `watch` 只在有待成交單時才進入 manage，鎖衝突時讓其中一次退出即可。
